# Decisions — Slice 5 (HUD + effects + win/lose wiring)

Ambiguities not pinned down by the PRD/architecture/design docs, resolved as follows while implementing this slice:

1. **HP-bar tween implementation strategy.** `view/unitView.js`'s `updateUnitGroup` snaps the HP-fill sprite to the true hp fraction every frame, and `sceneView.sync` (which calls it) runs *before* `effects.update` in the loop. Rather than editing `unitView.js`/`sceneView.js` to notify effects of hp deltas, `effects.js` tracks a per-unit "last-rendered" hp fraction and overwrites the same `hpFill` sprite (reached via `sceneView.unitGroups`, passed into `effects.update(dt, world, unitGroups)`) with an exponentially-smoothed value each frame, converging to the true value in ~150ms. This kept the allowed-edit footprint to effects.js/hud.js/main.js/loop.js plus the one sceneView death-fade edit, as the task explicitly offered this as the lower-friction option.

2. **Death "fade" is scale-to-zero + per-unit HP-sprite opacity fade, not whole-body opacity fade.** `unitView.js`'s body/prop/disc/selection-ring geometries *and materials* are intentionally shared across every unit of a given type/faction (its cache comment is explicit that disposing/mutating them would break other live units). Fading a shared material's opacity would fade every unit sharing it, not just the dying one. So `effects.playDeath` scales the whole Group to zero (always per-instance) and additionally fades the two per-unit ("ownedMaterial") HP-bar sprite materials, then disposes only those owned materials — consistent with the GPU-leak-free constraint already documented in `sceneView.js`.

3. **Move marker centroid, player-only trigger.** A move order's `moveGoal` is read per-unit off `world.units` (effects has no direct hook into `sim/orders.js`). A new move order is detected by reference-comparing each unit's `moveGoal` to its last-seen value (a fresh object is written on every `issueMove`, even re-clicking the same spot, so reference-compare — not value-compare — lets repeat clicks re-trigger the marker). Only `faction === 'player'` moveGoal changes spawn a marker; enemyAI's leash-disengage "walk home" order (architecture §4.6) also writes `moveGoal` and would otherwise spam a marker on every enemy retreat, which is not what design §5.1 is describing. Multiple selected units moving together in the same tick resolve to one marker at the centroid of their (jittered) goals, matching design §5.1's "one shared marker."

4. **Attack ring driven off `world.selection` + `attackTargetId`, read in `effects.update`**, not off explicit calls from the input layer — lower friction since the fields already exist on every unit (architecture §4.4) and `effects.update` already walks `world.units` every frame for the HP tween. Supports multiple simultaneous rings if different selected sub-groups target different enemies (design §5.2 doesn't say to cap this at one).

5. **Selection panel's "1 unit selected → enlarged slot + text line"** (design §2) was not implemented; all slot counts (1–6) use the same uniform slot markup (portrait + mini HP bar) that the slice brief explicitly scoped ("each slot shows the unit type (label/icon) + a mini HP bar"). The enlarged single-slot treatment is a presentation nicety, not called out in this slice's instructions, and skipping it keeps the change surface minimal.

6. **Portrait "icon"** is a single bold letter (`M` for melee, `R` for ranged) rendered as text inside the existing `.portrait` div, rather than a drawn icon/sprite — avoids any new asset or canvas-texture work for a HUD slice that is explicitly DOM-only.

# Decisions — Camera pan-into-void fix (QA bug, PRD §4.6 / US-9)

1. **Extracted `footprintInsets()` into a new file, `view/cameraMath.js`.** `camera.js` imports `three`, which only resolves via the browser's import map (`/vendor/three.module.js`), not under `node --test`. Splitting the pure trig into its own `three`-free module keeps it unit-testable; `camera.js` imports `footprintInsets` (and the pre-existing `DEG_TO_RAD` constant, moved there too to avoid duplicating it) from it.

2. **Symmetric inset per axis, using the worst-case (largest) half-extent**, exactly as specified: `halfD` is `max(near-edge reach, far-edge reach)` and `halfW` is measured at the far (widest) edge. This is intentionally conservative — it under-utilizes the near side's smaller true half-extent — but guarantees no void on the far side, which is the side that mattered in the reported repro.

3. **Degenerate case (footprint half-extent > map half-size on an axis) falls back to centering that axis**, per the task's explicit instruction. Important finding from browser verification: with the *current* `CAMERA_PITCH_DEG` (55°) / `CAMERA_FOV` (50°) / `CAMERA_DISTANCE` (60) constants and a typical 16:9 viewport, this degenerate case is hit on **both axes already at the default zoom level** (distance 60), not just at extreme zoom-out — `footprintInsets` computes `halfD ≈ 50.8` and `halfW ≈ 66.5` at distance 60/aspect 1.6, both well past the map's half-size of 24. So at default zoom, panning is now fully centered (a no-op) rather than revealing extra void. This fix verifiably stops panning from ever showing *more* void than the camera already shows at rest (confirmed via headless-browser screenshots — panning to any edge at default zoom now produces pixel-identical output to the unpanned baseline), which is what the reported bug and its repro steps describe. However, it does **not** eliminate a separate, pre-existing issue: even the unpanned default view already shows a large void region (~58% of the frame, concentrated at the top and side edges) because the frustum footprint at distance 60 is inherently larger than the 48×48 map given the current pitch/FOV. Fixing that would require retuning `CAMERA_DISTANCE`/`CAMERA_PITCH_DEG`/`CAMERA_FOV`/`MAX_DISTANCE` or enlarging the map — explicitly out of scope here ("keep pitch/yaw constants untouched"; the task also didn't ask for distance retuning). Flagging this as a follow-up candidate. Panning is fully functional and void-free once zoomed in enough that the footprint fits the map (confirmed at `MIN_DISTANCE`=20, where corner-panning shows 0% void, down from a two-axis void at the same zoom pre-fix).
